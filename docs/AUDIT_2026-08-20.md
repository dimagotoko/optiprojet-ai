## 3. Points ouverts confirmés

### 3.1 Véhicules ajoutés depuis `edit-trip` — incomplets (le plus concret)

**Constat vérifié aujourd'hui :**

- `src/app/post-trip/page.tsx:9,244` → utilise `vehicleSchema` complet (avec `type`, `province`).
- `src/app/edit-trip/[tripId]/page.tsx:10,200` → utilise encore `vehicleBaseSchema` (aliasé
  `vehicleSchema` localement), **sans** `type` ni `province`.
- `handleAddVehicle` (`edit-trip/[tripId]/page.tsx:263-296`) fait un `setDoc(vehicleRef, {...values, imageUrl, ownerId, createdAt})`
  — `type`/`maxSeats` jamais écrits pour un véhicule créé depuis cet écran.
- Aucun chemin de modification d'un véhicule existant (`edit-trip` ne fait que créer, jamais `update`/`set` sur un véhicule déjà en base).

**Impact réel (audit Firestore 2026-08) :** 5 véhicules sur 14 (36 %) sans `type`/`maxSeats`.
Le fallback `selectedVehicle?.maxSeats ?? 8` (`post-trip/page.tsx:631`) permet à un transporteur
avec un véhicule legacy de publier jusqu'à 8 places sur une berline — chiffre vu et cru par
les voyageurs.

**À faire :** ajouter `type` (+ calcul `maxSeats`) au formulaire `edit-trip`, et/ou créer un
vrai chemin d'édition de véhicule existant pour permettre aux véhicules déjà en base d'être
complétés (sans migration silencieuse).

### 3.2 Plafond prix légal QC — non vérifié côté serveur

`firestore.rules` → `isValidTrip()` vérifie `pricePerSeat × availableSeats ≤ 0,54 × distanceKm`,
mais `distanceKm` est fourni par le client — falsifiable. Aucune Cloud Function `onTripCreate`
trouvée dans le repo (vérifié : aucun fichier ne matche `onTripCreate`/`onDocumentCreated`).

**À faire (v1.x) :** Cloud Function qui recalcule `distanceKm` (haversine) à partir des
coordonnées, compare à la valeur cliente, rejette si écart > 5 %.

### 3.3 Expiration de session serveur sans déconnexion client

`src/lib/auth.ts` → le `catch` de `getCurrentUser()` vide le cookie `__session` côté serveur
uniquement (`cookieStore.set('__session', '', { maxAge: 0 })`) — vérifié toujours présent tel
quel. Aucun appel `signOut(auth)` ni désinscription du token FCM côté client.

**Risque :** un appareil peut continuer à recevoir des notifications push après expiration de
la session serveur.

**À faire :** intercepteur sur les réponses 403 côté client qui appelle `logout()`
(`src/lib/logout.ts`).

### 3.4 Notifications perdues si l'onglet se ferme trop vite

`TripDetailsClient.tsx` / `DemandesEnAttente.tsx` déclenchent un `fetch(...).catch(() => {})`
fire-and-forget juste après l'écriture Firestore. Si l'onglet se ferme entre les deux, la
requête ne part jamais. Le flag d'idempotence (`notifiedAt`/`statusNotifiedAt`) protège du
spam en cas de double appel, pas de cette perte.

**À faire :** trigger serveur (`onDocumentCreated`/`onDocumentUpdated`) indépendant du fetch
client.

### 3.5 Stat "CO₂ évité" — forfait fixe au lieu de la distance réelle

Vérifié : `src/components/dashboard/voyageur/VoyageurDashboard.tsx:61,422` —
`CO2_PER_TRIP_KG = 18` fixe, `co2Saved = acceptedCount * CO2_PER_TRIP_KG`. Chaque booking
accepté stocke pourtant déjà `distanceKm` réel (haversine, utilisé par "Argent économisé"
depuis le commit "feat - Argent économisé").

**À faire :** remplacer par `distanceKm * CO2_PAR_KM_SOLO` (≈ 0,12 kg/km). Prérequis : les
bookings créés avant la dénormalisation de `distanceKm` n'ont pas ce champ (même contrainte de
backfill que `pricePerSeat`).

### 3.6 `requireUser()` — aller-retour réseau superflu

Vérifié : `src/lib/auth.ts` → `requireUser()` appelle `getCurrentUser()` qui appelle
`verifySessionCookie()` **puis** `getAdminAuth().getUser(decodedIdToken.uid)`. Le second appel
est inutile pour les endpoints de notifications — l'`uid` est déjà dans le token décodé.

**À faire :** `getCurrentUid()` léger (sans `getUser()`) pour ces cas.

### 3.7 Purge des tokens FCM dormants

Vérifié : `lastSeenAt` (`users/{uid}/fcmTokens/{token}`, écrit dans
`src/app/api/notifications/token/route.ts`) n'est lu/utilisé nulle part pour purger. FCM
invalide un token après ~270 jours d'inactivité ; sans purge proactive, ces tokens morts
restent en base indéfiniment (le purge-sur-échec de `notify.ts` ne s'en charge qu'au prochain
envoi, jamais pour un utilisateur qui ne reçoit plus jamais rien).

### 3.8 Avatar véhicule généré (Proposition A) — décidée, non codée

`docs/PROPOSITION_PHOTO_VEHICULE.md` — décisions actées le juin 2026 : couleur en `<Select>`
fermé (option C2), avatar généré `VehicleAvatar` (fond = couleur, icône = mapping `type`).
Vérifié aujourd'hui : aucun composant `VehicleAvatar` dans `src/`. Le 6 août, la Proposition B
(upload photo réelle, `VehiclePhotoPicker`) a été implémentée à la place — la Proposition A
reste reportée, pas annulée.

## 4. Hors scope v1.0 — décisions explicites (pas des oublis)

- **Stripe Connect / paiements plateforme** — bloqué, 3 prérequis obligatoires non remplis
  (entité business NEQ, KYC conducteurs, validation cadre légal QC). Ne pas proposer
  d'intégration tant que non validés.
- **Page de préférences de notifications** (mute par type d'événement) — tout ou rien
  aujourd'hui (permission navigateur).
- **Rappels de trajet programmés** — nécessite Cloud Scheduler (déclenchement temporel, pas
  événementiel), hors périmètre v1.
- **Safari iOS** — push web nécessite l'installation en PWA (limitation plateforme, à
  mentionner dans l'UI d'opt-in).
- **Protocole d'accord — versioning v2** — pas de re-acceptation exigée en v1 si la version
  change ; comportement intentionnel, à trancher si/quand une v2 existe.
- **Pagination `/trips` — filtres client-side** — acceptable au volume actuel ; basculer les
  filtres principaux côté serveur (index composites ou Algolia/Typesense) seulement quand le
  volume grandira.
